# Define the CodeIgniter engineering alignment contract

## Outcome

Deliver a repository-specific engineering contract for adoption by default, with concrete adaptations, evidence,
remaining human choices and independently verifiable follow-on implementation boundaries. The maintainer's
2026-10-24 direction favors wholesale shared-practice adoption while retaining CodeIgniter's standard approach;
justify each deviation rather than treating every practice as an optional preference. Cite the inspected Agent OS
revision; local authority and public-package contracts remain binding. This is a decision/documentation chore,
normally one PR, not enforcement. [TICKET-00009](../tickets/00009-TICKET.md) retains contract acceptance and actual
implementation obligations after this proposal is complete.

## Scope

- In scope: an adopt/adapt/reject/defer rule matrix; ownership and inward dependency boundaries; direct package
  use versus genuine orchestration; PHP/naming conventions; meaningful test responsibilities and coverage policy;
  compatible PHPCS/PHPStan/Deptrac/Rector recommendations; shared-service/injection and bus-pipeline rules;
  gate phases, parity, exceptions and migration cost. Adopt compatible shared intent; adapt concrete framework
  mechanisms, defer only evidenced blockers and reject only justified non-applicable/conflicting assumptions.
- Use TASK-00009's release/contract findings. Inspect current local rules, source/test boundaries and tooling
  configuration, and reconcile the legacy T-00005 proposal through read-only evidence without importing it.
- Reconcile the incoming upstream legacy T-00007 requirement set preserved in
  [UPSTREAM-RECONCILIATION.md](../UPSTREAM-RECONCILIATION.md), including exact 100% Unit-only coverage,
  coverage metadata, Common/FightCommon PHPCS integration and tooling/suite phases. Do not silently accept or
  drop those requirements; they are distinct from the separate dirty T-00005 proposal. Explicitly compare the
  Unit-only 100% proposal with Agent OS's all-suite meaningful Domain/Application metric and separate unit
  attribution. Broad adoption approval does not silently choose between them or weaken existing requirements.
- Record durable findings/proposed contracts in repository documentation and link them from TICKET-00007 and this
  TASK. Distinguish the approved adoption direction from concrete unresolved policy choices and implemented
  enforcement. Coordinate delivery/report substitutions with TICKET-00010's shared Pi binding; do not copy the
  provider skill suite, hardcode private paths, or treat provider tests as target verification.
- Out of scope: installing tooling, modifying build/hosted gates or runtime code, dependency upgrades, test
  reorganization, bulk source moves, speculative HTTP/authorization features, and application journey development.
  Do not restore receipts, dependency-lane certification, pre-submit dependency maintenance, or tool-self-tests.
