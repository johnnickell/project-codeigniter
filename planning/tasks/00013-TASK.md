# Integrate CodeIgniter's shared Pi workflow binding

## Outcome

Deliver one independently reviewable compatibility slice: a concise target-owned shared-workflow binding,
narrow runtime ignores, and direct routing/delivery walkthrough evidence. Contributors can use installed Pi
skills without importing another project's framework, runtime, planning authority or delivery claims.
This TASK completes the accepted implementation scope of [TICKET-00010](../tickets/00010-TICKET.md), not the
broader package and engineering adoption in [EPIC-00002](../epics/00002-EPIC.md).

## Scope

- Add a short binding reachable from `AGENTS.md`, using actual supplied capability metadata/settings to locate
  provider resources. Keep shared instructions provider-relative and target rules local; no copied skill suite,
  private installation paths or mandatory repository-local `.pi/` directory.
- Bind CodeIgniter framework ownership, repository commands, planning vocabulary, branch/worktree rules,
  canonical review/QA evidence, completion, hosted checks and publication authority to local guidance.
- Cover planning, research, design and inspection boundaries plus work, independent review, applicable QA and
  land. Distinguish explicit `/skill:build` coordination from the local `./bin/build` command; `next` only routes.
- Document native Pi selection and the retained `fight-terminal` RPC refusal of `/skill:...`, including its
  native-selection/resume procedure. Distinguish actual capabilities from discovery, version parity and native
  Herdr companions; do not claim child/log observation without evidence.
- Replace the existing blanket `/var` ignore with narrow `/var/terminal/` and `/var/herdr-workspace/` ignores,
  after checking tracked content and other runtime needs. Retain any other justified generated-path ignores
  explicitly, without hiding unrelated application files. Preserve all existing operator/runtime files.
- Record instruction walkthroughs separately from actual native discovery/status observations and probes;
  update contributor documentation and affected planning handoffs without duplicating provider instructions.
- Out of scope: package upgrades, application behavior, engineering coverage/tool enforcement, global settings
  or installation, copied package/skill source, new runtime isolation, proxy implementation, credential access,
  enrollment, paid probes, publication, release and retired framework-support certification.
